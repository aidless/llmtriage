# 路线图：先做大，再求精简（2026-11-01）

一句话：`llmtriage` 现在能回答「哪里不对」（gpu / logs / budget / probe / metrics / slo），
还差「凭这些证据最可能是什么原因、下一句敲什么」（`explain` 已落地），以及「事后能不能
重放与复核」（未做）。

本文件是**判据来源的地图**：每个新能力都要指回一篇论文或一条明确的工程约束，指不回去的
不做。反过来，论文里我们**没有采纳**的部分也写在这里 —— 免得日后误以为"参考过就等于做了"。

---

## 1. 为什么是这三块，而不是别的

LLM 推理排障的三层现实（2026-11-01 在 GitHub 上实测星数得到的生态分布）：

| 层 | 代表项目 | 它们解决什么 | 它们不解决什么 |
|---|---|---|---|
| 引擎 | vLLM 95,971★ / SGLang 38,321★ / Dynamo 8,413★ | 把吞吐做上去 | 出问题时告诉你「为什么」 |
| 观测 | nvitop 7,235★ / dcgm-exporter 1,920★ / gpustat 4,390★ | 指标采集与展示 | 给出结论与下一步 |
| 基准 | llmperf 1,127★ / inference-perf 266★ | 压出数字 | 数字不达标时怎么办 |

三层都**默认「部署已经跑起来了」**。真实现场的卡点恰恰在那之前与那之后：
起不来（假线索、依赖残缺）、跑得不对劲（在 CPU 上算、被判据卡住）、要复盘（根因未定就不能
说已修复）。这三格是 `llmtriage` 的全部存在理由，也是本次"做大"的方向。

## 2. 论文 → 功能映射（做了什么 / 没做什么）

### 2.1 `metrics`：把 `/metrics` 变成结论（已落地）

- **DistServe**（arXiv 2401.09670）：goodput = 同时满足 TTFT 与 TPOT 的请求占比；分离
  prefill/decode 以消除 PD 干扰。
  → 采纳：占位概念（排队 / KV 占用 / 抢占）。
  → 未采纳：PD 分离本身（那是引擎与部署拓扑的事，不是分诊工具该改的）。
- **LUMINOS**（SSRN 7466083）：把 LLM 推理的 SLI/SLO 定义清楚（承运级网管场景）。
  → 采纳：SLI 命名与"先定义再测量"的纪律。
- **LatencyPrism**（arXiv 2601.09258）：零侵入延迟分解 + 异常预警。
  → 采纳：只读、零侵入（我们只读 `/metrics` 与日志）。
  → 未采纳：它的分解能力需要插桩，不在本工具范围。
- **实测教训**：vLLM 的 KV 指标在不同版本里叫 `gpu_cache_usage_perc` 或 `kv_cache_usage_perc`。
  只认一个名字 = 升级后静默失明。这与 `gpu.py` 里「按列名子串匹配、按列位置匹配会静默错位」
  是同一个 bug 家族，所以别名表是硬编码的、并有测试钉住。

### 2.2 `slo`：把 tok/s 换成 goodput（已落地）

- **DistServe**：goodput 定义（同上）。
- **LSSP**（Research Square，2026）：调度器排名跨工作负载/指标不可移植（τb 0.419，
  top-policy 一致率 31.9%）。
  → 采纳为**诚实边界**：本模块只算不测；batch=1 的延迟不能外推到高并发；结论必须带样本
  来源，否则不许引用。
- **TaiChi**（arXiv 2508.01989）：紧 TTFT 松 TPOT 该聚合、反之该分离。
  → 采纳为 `binding` 字段：说清是 TTFT 还是 TPOT 在拖后腿，因为两者对应的修法完全相反。
- **未采纳**：Kairos/SERVE-BENCH 的突发/多租户公平测试矩阵 —— 那需要负载生成器，是
  inference-perf 的地盘，我们不重造。

### 2.3 `explain`：证据 → 排序假设 → 下一句检查（已落地）

- **Cloud-OpsBench**（arXiv 2603.00468）：evidence-grounded 云 RCA benchmark，754 例 /
  57 故障类型，按状态快照重放。
  → 采纳：假设必须挂证据（`from_findings` 只能是真实存在的 finding kind，有测试）。
  → 未采纳：它的 754 例语料与重放机制（我们还没有回放器，见 §3）。
- **GALA+**（ASE 2026）：图约束 RCA，输出 **ranked diagnoses + next action**。
  → 采纳：输出形态就是"排序假设 + 可执行下一步"。
  → 未采纳：图模型（我们的规则表是确定性的、可读的、可被用户改的；引入模型会让"为什么
  给这条"变成黑箱，与"不许编原因"冲突）。
- **CloudIR-Bench**（arXiv 2610.29185）/ **AIOpsLab**（arXiv 2501.06706）：
  → 只作背景：说明"事故报告 → 根因 + 缓解"是被公认的评测对象，不是我们发明的需求。

### 2.4 顺带修正的一个真缺陷

`test_gpu_backend_falls_back_to_rocm_when_nvidia_missing` 本机红、CI 绿：PATH 写成
`<tmp>:/usr/bin:/bin`，本机存在 `/usr/bin/nvidia-smi` 就会走 NVIDIA 分支。改成隔离 bin
目录，并补一条反证（两个后端都在时必须优先 NVIDIA）。**"本机绿 CI 红"与"本机红 CI 绿"
一样是测试在说谎。**

## 3. 还没做的（按价值排序，不是按难度）

1. **`bundle`：可复核证据包**（Cloud-OpsBench 的"evidence-grounded"落到工程上）
   把 triage.json + 原始 `/metrics` 文本 + 日志尾部 + 环境指纹（驱动/rocm-smi/引擎版本）
   打成一个带 sha256 清单的目录，供事后复核与贴给上游。
   验收：同一份输入两次生成，清单哈希一致；缺任何一件时明确标注"缺"，不是静默省略。
2. **`replay`：状态快照重放**
   把一次分诊的输入（日志行、指标文本、GPU CSV）固化为 fixture，重跑必须给出同样的判定。
   这既是回归测试，也是 Cloud-OpsBench 式评测的最小可用形态。
3. **故障类型表（fault taxonomy）**
   目前规则表覆盖 8 类（依赖残缺/父进程异常/过载/KV 压力/未就绪/预算不匹配/SLO 不达标/
   GPU 空载）。要扩到 57 类不现实，但可以按"现场最常见"扩到 15-20 类，每类附一条反例
   （什么现象出现时**不该**判成它）。
4. **真机补 `in_use` 路径**
   2026-11-01 尝试 5 次全被调度器撤单（`202 allocating` → 2.5 分钟后 `not_found`），
   所以 AMD 上的 `in_use` 判定至今只有桩程序证据。**这一格空着就空着，不写"已验证"。**

## 4. 再求精简（下一轮要做的减法）

做大之后表面变宽了，减法是必须的，但要**先有测试再删**。具体清单：

- 子命令 8 → 5：`metrics`/`slo`/`explain` 的独立入口保留（它们各自可单跑），
  但 `gpu`/`probe`/`logs`/`budget` 四个薄封装可以收进 `triage --only gpu,logs`；
  要求：收掉后每个旧命令的退出码语义有等价测试。
- `report.py` 与 `explain.py` 的 Markdown 渲染有重复的表格/列表拼装 → 抽一个 `md.py`。
- 阈值常量目前散在 `gpu.py`（0.15/20）、`metrics.py`（0.90/8）、`budget.py`（0.2 余量）
  → 集中到一个 `thresholds.py`，并在文档里标明"都是启发式，不是论文结论"。
- 删掉 `metrics.py` 里 README 未使用的别名项（保留有测试覆盖的那些）。

**减法的验收标准**：测试数不减少（删代码不删覆盖），每个被删入口有一条"旧用法仍然可用
或已明确废弃"的说明。

## 5. 判据边界（写在这里，防止日后自我美化）

- 阈值（KV 0.90 / 排队 8 / 显存 15% / 利用率 20 / 20% 余量）**全部是我们定的启发式**，
  没有一篇论文给出这些分界线。改之前先测自己集群的基线。
- `slo` 的 goodput 只对给定样本成立；样本怎么来的，结论就只到哪。
- `explain` 的假设是**排序的建议**，不是诊断结论；每条都必须能被执行一次检查推翻。
- 真机证据只有一格：W7900 空载采样（`docs/evidence-rocm-w7900-2026-11-01.md`）。
